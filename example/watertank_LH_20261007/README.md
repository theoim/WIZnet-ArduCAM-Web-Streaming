# 저수조 부저 감시 장치 — 현장 빌드 (2026-10-07)

`example/WIZnet_WaterTank`에서 갈라져 나온 **현장 설치용 빌드**다. 날짜를 디렉토리
이름에 박아둔 이유는 하나다 — **현장에 나간 펌웨어가 어떤 소스였는지 나중에
정확히 짚을 수 있어야 한다.** 원본 예제는 계속 바뀌고, 이미 벽에 붙어 있는 박스는
안 바뀐다.

개발 경위와 검출 방식이 왜 세 번 바뀌었는지는 **`DEVELOPMENT.md`** 에 있다.
이 문서는 **그 이후에 달라진 것**과 **다음 요청이 왔을 때 어디를 고치는지**를 적는다.

## 하는 일

기존 저수조 부저가 울리면 **소리로 감지해서** Discord로 사진과 함께 알린다.
포트포워딩된 주소로 **실시간 영상**을 보여주고, 현장에서 **웹 패널로 설정**한다.

부저에 배선하지 않는다. 마이크로 듣는다.

## 세 가지 이미지

하나의 소스에서 `-D` 하나씩만 다르게 빌드한다.

| 타깃 | 코어 | 주소 | 용도 |
|---|---|---|---|
| `watertank_lh` | 1개 | 고정 | 회귀 기준. 검출 로직을 바꿨을 때 비교용 |
| `watertank_lh_dualcore` | 2개 | 고정 | **현장용** |
| `watertank_lh_dhcp` | 2개 | DHCP → 실패 시 고정 | 현장 네트워크를 모를 때 |

세 개를 USB에 담아 가면 현장에서 한 번에 끝난다. 두 번째 방문이 훨씬 비싸다.

```
cmake --build build --target watertank_lh_dualcore watertank_lh_dhcp watertank_lh
```

> **Debug로 빌드한다.** 아래 "알려진 문제" 참조.

## WaterTank 예제와 달라진 것

### 1. 두 코어로 나눴다

```
core 0   마이크만. I2S DMA, Goertzel, 검출기, 부저 LED
         절대 블로킹하지 않고, 할당하지 않고, 플래시나 네트워크를 건드리지 않는다

core 1   기다리는 것 전부. 웹서버, 카메라, TLS, 설정 저장
         몇 초씩 멈춰도 core 0의 블록 수신을 막지 못한다
```

왜 나눴는지는 측정값 한 줄이 말한다:

```
[audio] 50 buffers lost during the startup message (6400 ms of sound)
```

Discord 한 통은 DNS + TLS 핸드셰이크 + 45 KB 업로드다. 한 코어에서는 **그동안
마이크를 안 읽는다.** 6\~8초. 그게 **부저가 울린 직후**라면, 두 번째 울림이
그 구멍에 들어간다.

규칙은 `xcore.h`에 전부 적어뒀다. 요약하면:

- **W6300은 core 1 전용.** 두 코어가 하나의 QSPI를 건드리면 칩 트랜잭션 중간에
  레지스터 쓰기가 섞인다
- **카메라도 core 1 전용.** 같은 이유 + 호출자가 둘 다 core 1이다
- **플래시 쓰기는 core 0을 멈춘다.** 섹터를 지우는 동안 XIP 창을 못 읽고,
  core 0은 거기서 실행된다. `multicore_lockout_victim_init()` 필수
- **1초 타이머를 core 1로 옮겼다.** 타이머 콜백은 풀을 만든 코어에서 돈다
- **core 0은 할당하지 않는다.** malloc 뮤텍스를 mbedTLS가 쥐고 있으면
  core 0이 거기서 기다린다 — 이 분리가 없애려던 바로 그 정지다

### 2. 경보 재전송

**전에는 한 번 보내고 끝이었다.** 공유기가 재부팅 중이거나 회선이 1분 끊기면
경보가 그대로 사라졌다. 아무도 안 보는 콘솔에 `FAILED` 한 줄 찍고.

**이 제품에서 가장 나쁜 고장이다.** 그동안에도 제품은 정상으로 보인다.

```c
#define ALERT_RETRY_MAX      20
#define ALERT_RETRY_DELAYS   { 10, 30, 60, 120, 300 }   /* 초 */
#define CLEAR_RETRY_MAX      3
```

10초 → 30초 → 60초 → 120초 → 300초, 마지막 간격을 반복해서 **약 1시간 40분**
시도한다. 원인마다 길이가 다르기 때문에 간격을 늘린다 — 공유기 재부팅은 1분이면
돌아오고, 회선 장애는 아니고, 둘 다 10초마다 두드린다고 나아지지 않는다.

**큐가 아니라 슬롯 하나다.** 이 메시지들은 사건이 아니라 상태다 — 쓸모 있는
메시지는 언제나 "지금 부저가 울리고 있다"이므로, 새 경보가 못 보낸 이전 것을
**덮어쓴다.** 밀린 목록을 관리할 필요가 없다.

**사진도 보관하지 않는다.** 45 KB를 한 시간 들고 있다가 한 시간 전 사진을 보내는
건 의미가 없다. 재시도할 때 새로 찍는다 — 보는 사람이 원하는 건 그쪽이다.

**경보가 상황종료보다 우선한다.** 경보가 못 나갔는데 "상황 종료"만 도착하면,
그게 물이 찬 저수조에 대해 주인이 듣는 첫 소식이 된다.

### 3. Discord 타임아웃 30초 → 8초

정상 연결은 13 ms에 끝난다. 30초는 **네트워크가 죽었을 때 core 1을 32초간 묶는
값**이고, 그동안 웹 패널과 라이브 영상도 같이 멈춘다. 빨리 실패하고 나중에
다시 하는 쪽이 낫다 — **재시도가 생겼으니 "나중에"가 실제로 있다.**

### 4. 진단 출력

현장에서 콘솔 하나로 상태를 읽을 수 있어야 한다.

```
[alive] core0 62 blk/s   core1 14874 laps/s   ovr 0
```

30초마다. **두 코어가 다 도는지**가 핵심이다. 조용한 콘솔과 멈춘 보드가
구분되지 않으면 아무 의미가 없다.

이상하면 뒤에 붙는다:

```
   STUCK in alert for 30076 ms                    core 1이 멈췄다. 어디서인지도
   SLOW: worst idle 7056 ms, now in web 12 ms     느리다. 어느 단계가 범인인지
```

`laps/s`가 100 미만이면 "느림"으로 본다. **멈춘 것보다 느린 쪽이 잡기 어렵고,
실제로 그게 일어났다.** 초당 2만 번 돌던 코어가 1번 도는데 아무 데도 안 걸려
있는 상태.

부팅 때는 리셋 사유를 찍는다 (`POWMAN chip_reset`):

```
reset cause: POR   (0x00000100)
```

워치독인지 전원인지 글리치인지가 구분된다. **"혼자 재부팅됐다"는 증상에서
제일 먼저 필요한 정보다.**

### 5. 현장에서 조정한 검출 임계값

`detector.c`는 **현장에서 실제 부저 소리로 맞춘 값**이다. 벤치 기본값과 다르다.

```c
d->cfg.loud_k        = 2.2f;              /* 베이스라인 대비 배수 */
d->cfg.loud_hits     = bps * 1.0f;        /* 3초 창에서 1초 이상 */
d->cfg.window_blocks = bps * 3.0f;        /* 3초 슬라이딩 창 */
```

```c
#define CLEAR_SECONDS  7.5f    /* 이만큼 조용하면 감시 모드로 */
#define LEARN_SECONDS  5       /* 부팅 후 방 소리를 배우는 시간 */
```

**음조성(tone) 경로는 꺼져 있다.** 실제 부저에서 음조성 지표가 작동하지 않는 것이
확인됐다 — 경위는 `DEVELOPMENT.md` 3-2절에 있다. 지금 동작하는 것은
**음량 + 지속시간**이다.

### 6. 코드 정리

- `mic_i2s.c/.h` 삭제 — 독립 마이크 테스트용이었고 여기서는 컴파일되지 않았다
- `STREAM_LINGER_SEC` 삭제 — 읽는 곳이 없었다
- `discord.c`의 소켓 번호가 `0`이었다 → `SOCK_HTTPS`
- **CMake 타깃을 함수 하나로** — 세 번 복사돼 있었다. 누가 파일 하나를 추가하면
  이미지 하나만 조용히 그 기능이 빠진 채로 빌드된다
- **`webserver.c`에서 HTML/CSS/JS를 `web_page.h`로 분리** — 49 KB → 32 KB.
  CSS 한 줄 고칠 때마다 C 문자열 안의 따옴표를 세는 일이 없어졌다

## 현장 설정

### 배포 전 확인 ★

**`config.h`의 주소가 지금 사무실 값이다.**

```c
#define NET_IP        { 192, 168, 11, 9 }
#define NET_GATEWAY   { 192, 168, 11, 1 }
```

현장 대역으로 바꾸고 빌드해야 한다. **모르면 `watertank_lh_dhcp`를 가져간다.**

### `secrets.h`

`secrets.h.example`을 복사해서 채운다. **`secrets.h`는 커밋되지 않는다**
(`.gitignore`).

| 값 | 필수 | 비고 |
|---|---|---|
| `STREAM_TOKEN` | **예** | 없으면 부팅을 멈춘다. 토큰 없는 카메라를 포트포워딩에 노출시키지 않는다 |
| `WEBHOOK_URL` | 아니오 | 비워도 감시·패널·로그는 동작한다. **CONFIG 탭에서 넣는 쪽이 낫다** — 웹훅 바꾸려고 펌웨어를 다시 굽지 않아도 된다 |
| `PUBLIC_URL_BASE` | 아니오 | Discord 메시지의 링크가 눌리는지만 결정 |

### 주요 설정값

| 항목 | 기본 | 위치 |
|---|---|---|
| 경보 해제 무음 | 7.5초 | `CLEAR_SECONDS` |
| 부팅 학습 | 5초 | `LEARN_SECONDS` |
| 음량 바닥 | −40 dB | `DET_FLOOR_DB_DEFAULT`, 패널에서 조정 가능 |
| 카메라 해상도 | HD | `CAM_RES_DEFAULT 3` |
| 스트림 간격 | 100 ms | `STREAM_MIN_INTERVAL_MS` |

**`STREAM_MIN_INTERVAL_MS`는 두 번 함정이었다.** fps가 느리다고 최적화를 의심했는데
두 번 다 `config.h`를 교체하면서 이 값이 500으로 되돌아간 것이었다.

## 알려진 문제

### Release(-O3)로 빌드하면 동작하지 않는다 ★

같은 소스, 같은 보드에서 A/B 했다:

| | laps/s | fps | 결과 |
|---|---:|---:|---|
| Debug (`-Og -g`) | 14,874 | 10 | 정상 |
| Release (`-O3 -DNDEBUG`) | 1 | — | 접속 거부 |

**원인 미파악. Debug로 배포한다.**

다음 실험: `RelWithDebInfo`(`-O2`), `-fno-strict-aliasing`. 둘 중 하나가
경계를 좁혀줄 것이다.

### 웹훅 URL이 로그에 전체가 찍힌다

`port/wiz-claw/src/wiz_claw_http.c`가 전송마다 URL 전체를 출력한다.
**웹훅은 그 Discord 채널의 비밀번호다.** 로그를 복사해서 붙이는 순간 노출된다.

가려야 한다. 그리고 **노출된 웹훅은 재발급이 유일한 복구다.**

### 워치독 없음

두 코어가 다 돌 때만 먹이는 워치독이 필요하다. 지금은 core 1이 멈추면
`[alive]`에 `STUCK`으로 보일 뿐 스스로 복구하지 않는다.

### DHCP 리스 갱신 없음

받은 주소를 고정처럼 쓴다. 리스가 만료되고 공유기가 그 주소를 다른 장비에 주면
전원 재투입이 필요하다. **공유기에 DHCP 예약을 거는 것이 올바른 해법이다.**

### 야간 사진

ArduCAM Mega의 IR 차단 필터 때문에 적외선 LED는 효과가 없을 가능성이 높다.
조명이 필요하다.

## 다음 요청이 왔을 때

어디를 건드리는지.

| 요청 | 파일 | 비고 |
|---|---|---|
| 감도가 둔하다 / 예민하다 | 패널 MIC·CAM 탭 | **코드 수정 없이 현장에서.** dB/주파수가 1초마다 표시되므로 보면서 맞춘다 |
| 경보 해제가 너무 빠르다/느리다 | `CLEAR_SECONDS` | |
| 알림 문구 | `main.c`의 `alert_alarm()` / `alert_clear()` | |
| 재시도 간격·횟수 | `config.h`의 `ALERT_RETRY_*` | |
| 해상도 | 패널 또는 `CAM_RES_DEFAULT` | 해상도는 즉시 적용, 주소는 재시작 |
| 주소 대역 | `config.h`의 `NET_*` | 또는 dhcp 이미지 |
| 패널 화면 | `web_page.h` | `PAGE_HEAD` = 마크업·CSS, `PAGE_SCRIPT` = 동작 |
| 새 API 엔드포인트 | `webserver.c` | 페이지 문자열은 이제 여기 없다 |
| 검출 알고리즘 | `detector.c` | **`watertank_lh`(단일코어)로 회귀 비교할 것** |

### 작업할 때의 규칙

1. **core 0에 블로킹·할당·플래시·네트워크를 넣지 않는다.** `xcore.h` 참조
2. **추측으로 고치지 않는다.** 이 프로젝트에서 추측으로 맞힌 원인은 하나도 없다
3. **`secrets.h`를 커밋하지 않는다**
4. **Debug로 빌드한다**

### 핀 배치

| 신호 | 핀 |
|---|---|
| I2S BCLK | GP2 |
| I2S WS | GP3 (BCLK+1, PIO가 연속 핀을 요구한다) |
| I2S SD | GP28 |
| 부저 감지 LED | GP25 |
| RUN LED | GP26 |

카메라와 W6300 핀은 TOE 스트리밍 예제와 동일하다.
