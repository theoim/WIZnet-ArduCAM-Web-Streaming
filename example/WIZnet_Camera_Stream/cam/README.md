# cam/ — 카메라 라이브러리

RP2350 + W6300(W6300-EVB-Pico2)에 붙는 DVP 카메라를 **카메라 종류와 상관없이 같은
스트리밍 코드로 쓰기 위한** 디렉토리다. 카메라를 바꿀 때 바꾸는 것은 빌드 옵션 하나이고,
웹서버·스트리밍·네트워크 코드는 그대로 둔다.

---

## 왜 이 디렉토리가 있나

지금까지 카메라 예제는 카메라마다 드라이버를 통째로 복사해서 만들었다.

```
WIZnet_ArduCAMMega_TOE_Web_Streaming/arducam_mega/arducam_mega.c   (LH 저수조도 이것을 컴파일)
WIZnet_OV2640_Exhibition/ov2640.c                                  (위 파일을 복사해 고친 것)
```

두 파일을 비교해 보면 **영상을 받는 부분(PIO·DMA·JPEG 끝 찾기)은 이름만 다르고 코드가
같다.** `image_mega.pio`도 바이트 단위로 같다. 실제로 다른 것은 센서에 무엇을 써서
해상도와 포맷을 정하느냐뿐이다. 그런데 복사본이라 버그를 한쪽에서 고치면 다른 쪽에는
남는다.

카메라가 OV5640, OV7640, HM01B0로 늘어날 예정이라 복사 방식으로는 감당이 안 된다.
그래서 세 층으로 나눈다.

| 층 | 무엇이 다른가 | 위치 |
|---|---|---|
| **센서 드라이버** | 칩 ID, 레지스터 테이블, 해상도·포맷 설정 | `cam/<sensor>/` |
| **모듈 핀맵** | 같은 센서라도 모듈 보드마다 다른 것: XCLK 오실레이터 유무, PWDN·RESET 핀, SCCB 속도 | `cam/modules/<module>.h` |
| **공통** | SCCB 접근, 칩 판별, DVP 캡처 | `cam/cam_sccb.*`, `cam/cam_probe.*`, (예정) `capture/` |

**센서와 모듈을 분리한 이유**: 같은 OV5640이라도 어떤 모듈은 오실레이터를 갖고 있고 어떤
모듈은 MCU가 XCLK를 만들어 줘야 한다. OV2640 전시 모듈은 오실레이터가 없어서 GP26에서
PWM으로 20 MHz를 공급하고, LH의 Arducam 모듈과 사용자의 OV5640 모듈은 자체 오실레이터가
있다. 이런 차이는 센서 레지스터와 무관하므로 핀맵 파일에 둔다.

## 지원 카메라와 상태

| 카메라 | SCCB 주소 | 레지스터 주소 폭 | 칩 내장 JPEG | 상태 |
|---|---|---|---|---|
| **Arducam Quick-Bootup 3MP DVP (B0554)** — LH 저수조 카메라 | 0x1F (모듈 제어칩) | 16비트 | 있음 (제어칩이 처리) | **`cam/arducam_qb/` 이전 완료, 실기 검증.** 1280x720 28.1 fps, 24,677프레임 드롭 0. 640x480 20~23 fps 16~17 KB, 드롭 0·손상 프레임(`r_err`) 0 (2026-10-22) |
| **OV2640** — 전시 카메라 | 0x30 | 8비트 | 있음 | **`cam/ov2640/` 이전 완료, 실기 검증.** 800x600 17.1 fps, 26,561프레임 드롭 0 (2026-10-22). 640x480은 UXGA 어레이를 읽어 5.9 fps |
| **OV5640** | 0x3C | 16비트 | 있음 | 칩 판별 코드 있음. 드라이버 작성 예정 |
| **OV7640 / OV7670** | 0x21 | 8비트 | 없음 | 칩 판별 코드 있음 |
| **OV3660** | 0x3C | 16비트 | 있음 | 칩 판별 코드 있음. 카메라 없음 |
| **HM01B0** | 0x24 | 16비트 | **없음** (흑백 raw, 저해상도) | 칩 판별 코드 있음 |

### Arducam 모듈은 성격이 다르다

LH 카메라(Arducam B0554)는 **이미지 센서를 직접 보여 주지 않는다.** SCCB 버스에는
모듈 위의 제어칩(0x1F)만 보이고, 호스트는 `RESOLUTION_REG` 같은 추상 레지스터에 값
하나를 써서 해상도를 바꾼다. 제어칩이 내부 센서를 대신 설정한다.

실측값 (2026-10-22, `camera_probe`):

```
SCCB scan: 0x1F                        ← 이것 하나만 응답
SENSOR_ID 0x039E   FIRMWARE_VER 0x02   ← 0x0000~0x0002
PIXEL_FMT 0x01 (JPEG)  RESOLUTION 0x03 (1280x720)
```

`0x039E`가 어떤 센서 품번인지는 Arducam이 공개하지 않았다. 그래서 OV5640 같은 직접 제어
드라이버로 이 모듈을 대신할 수 없고, 별도 드라이버(`cam/arducam_qb/`)로 둔다.

### 칩 내장 JPEG가 없는 센서

OV7640/7670과 HM01B0는 JPEG를 만들지 않는다. 그대로 보내면 raw 프레임이고, MJPEG
스트리밍을 하려면 MCU가 인코딩해야 한다. 그래서 공통 코드는 센서 이름이 아니라
드라이버가 알려 주는 능력(`has_jpeg`, `mono`, 최대 해상도)을 보고 경로를 정한다.
HM01B0는 대신 저전력·흑백이라 온디바이스 사람 감지 같은 Edge AI 실험에 맞는다.

## 파일

```
cam/
├─ README.md            이 문서
├─ cam_sccb.h / .c      SCCB 읽기·쓰기. 8비트/16비트 레지스터 주소, 타임아웃
├─ cam_probe.h / .c     버스 스캔 + 알려진 센서의 칩 ID 판별
├─ modules/
│  ├─ lh_arducam_qb3mp.h    Arducam B0554, 오실레이터 내장, XCLK 없음
│  ├─ ov2640_exhibition.h   OV2640, XCLK = GP26 PWM 20 MHz
│  └─ ov5640_dvp_module.h   OV5640, 오실레이터 내장 (주파수 표기 확인 필요)
└─ <sensor>/            센서 드라이버 (이전·작성 예정)
```

### SCCB에서 주의할 점

SCCB는 I2C와 거의 같지만 **repeated start를 쓰지 않는다.** 레지스터 주소를 쓰는
트랜잭션은 STOP으로 끝나고, 읽기는 별도 트랜잭션이다. `cam_sccb.c`의 모든 읽기가 이렇게
되어 있다. 교과서식 I2C(repeated start)로 바꾸면 센서가 응답하지 않는데, 로그에서는
배선 문제처럼 보인다.

모든 접근에 타임아웃(20 ms)이 있다. 장치가 없거나 버스가 멈춰도 프로브가 멈추지 않고
"응답 없음"을 보고한다.

## 빌드

카메라 모듈은 소스의 `#define`이 아니라 **CMake 옵션**으로 고른다.

```bash
cmake -S . -B build_cam_lh -G "MinGW Makefiles" -DCMAKE_BUILD_TYPE=Debug \
      -DCAMERA_MODULE=lh_arducam_qb3mp
cmake --build build_cam_lh --target camera_probe
```

**모듈마다 빌드 디렉토리를 따로 둔다**(`build_cam_lh`, `build_cam_ov2640` …). 한
디렉토리에서 옵션만 바꿔 쓰면 다른 카메라용 이미지를 플래시하는 사고가 생긴다. 같은 이유로
모든 이미지는 부팅 배너에 모듈 이름과 빌드 시각을 찍는다. 플래시 후 그 줄부터 확인한다.

`CMAKE_BUILD_TYPE=Debug`(`-Og`)를 쓴다. 이 저장소에서 `-O3`가 카메라 캡처를 오히려 느리게
만든 기록이 있다.

## camera_probe — 카메라를 바꿨을 때 가장 먼저 올리는 이미지

네트워크를 쓰지 않는다. 카메라 전원을 켜고, 버스를 스캔하고, 칩 ID를 읽어 USB 콘솔에
3초마다 출력한다. LAN에 연결하지 않은 보드에서도 쓸 수 있다.

| 출력 | 의미 |
|---|---|
| 알려진 주소 + 칩 이름 | 그 드라이버로 진행 |
| `0x1F` + `SENSOR_ID 0x....` | Arducam 모듈. ID가 0x039E가 아니면 다른 모델(5MP B0555 등)일 수 있다 |
| `nothing answered` | 3V3 전원 → PWDN Low → (오실레이터 없는 모듈이면) XCLK 순서로 확인. SDA/SCL은 그다음 |
| 응답은 있는데 알려진 카메라가 아님 | 주소를 확인해 `cam_probe.c` 표에 추가 |

---

## 새 카메라를 추가하는 방법

1. `camera_probe`로 SCCB 주소와 칩 ID를 먼저 확인한다. 데이터시트의 값을 믿기 전에 실물에서 읽는다.
2. `cam/modules/<module>.h`에 핀맵을 만든다. XCLK가 필요 없으면 `CAM_PIN_XCLK (-1)`로 두되,
   **오실레이터 주파수(`CAM_XCLK_HZ`)는 반드시 적는다.** 센서 PLL 설정이 그 값을 기준으로
   계산되므로, 틀리면 오류 없이 fps와 PCLK만 어긋난다.
3. `cam/<sensor>/`에 드라이버를 만든다. 칩 판별, 초기화, 해상도·포맷 설정, 능력 표시.
4. 해상도는 공통 해상도 목록으로 받고, 센서별 레지스터 값으로 바꾸는 표를 드라이버 안에 둔다.
5. `CMakeLists.txt`의 `CAMERA_MODULE` 목록에 추가한다.
6. 프레임 크기(KB)로 실제 해상도를 확인한다. 콘솔에 찍힌 해상도는 프로그램 변수일 뿐
   센서 상태가 아니다. 이전 예제에서 콘솔은 1280x720이라고 하는데 센서는 4 KB짜리 QVGA를
   보내고 있었던 적이 있다.

### 측정할 때 주의 (2026-10-22에 실제로 틀린 것)

- **스트림 페이지는 하나만 연다.** 스트림은 가장 최근 요청자 한 명에게만 간다. 페이지가 두 개 열려
  있으면 서로 스트림을 빼앗으며 10~15초마다 재연결한다(`/api/status`의 `r_idle` 증가). 이걸 손상
  프레임으로 오판해 클럭 분주를 바꿨다가 fps만 잃고 되돌렸다.
- **통과 기준은 `dropped` 0 그리고 `r_err` 0.** 장비는 JPEG의 시작·끝 표시만 검사하므로, 중간이 깨진
  프레임은 브라우저 쪽 `r_err`로만 보인다.
- 해상도를 바꾼 직후의 `fps`는 이전 설정의 창 평균이다. `frames`가 수백 이상 늘어난 뒤의 값을 쓴다.
- `stale`이 `true`면 촬영이 멈춘 상태의 옛 값이다. 측정값으로 쓰지 않는다.
