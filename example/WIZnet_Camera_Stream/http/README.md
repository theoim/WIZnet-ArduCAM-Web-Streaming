# http/ — HTTP 요청 파서 (Phase 1a)

`http_req.c/h`는 연결 하나에서 요청 하나를 받는 HTTP/1.x 요청 파서다.
데이터가 몇 조각으로 나뉘어 들어와도(TCP 수신 단위, TLS 레코드 단위) 순서대로 넣기만 하면 된다.
헤더와 선언된 본문이 모두 도착하고 정책 검사를 통과한 뒤에만 `HTTP_REQ_COMPLETE`를 돌려준다.

## 왜 필요한가

2026-10 기준 `server_toe.c`는 `tls_recv()`를 한 번 호출해 1 KB 전역 버퍼에 받은 내용에서 `GET ` 첫 줄의 경로만 잘라 썼다.
그래서 다음을 처리할 수 없었다.

- 여러 TLS 레코드로 나뉘어 온 요청
- 1 KB를 넘는 헤더(쿠키가 붙은 브라우저 요청)
- Cookie, Authorization 헤더
- POST 본문

로그인, 세션, 설정 저장 같은 이후 기능은 모두 이 파서를 전제로 한다.

## 파서 선택

| 후보 | 판단 | 근거 |
|---|---|---|
| ioLibrary `Internet/httpServer/httpParser.c` (저장소 내) | 사용 안 함 | 요청 전체가 한 버퍼에 있어야 함, `strtok`(재진입 불가), 길이 검사 없는 `strcpy`로 URI 복사(`httpParser.c:194`), 헤더 미해석 |
| picohttpparser (MIT/Perl 이중 라이선스, 약 700줄) | 사용 안 함 | 요청 줄·헤더 토큰화만 하고 본문·Content-Length 정책은 직접 만들어야 함. 부분 입력 시 매번 처음부터 다시 파싱(`last_len` 힌트). 허용 문법이 이 프로젝트 정책보다 넓어(예: obs-fold, 중복 헤더) 정책 계층이 따로 필요. 외부 의존성·라이선스 표기·버전 고정 부담 |
| 직접 구현 | **선택** | 의존성 0(`<string.h>`만), ARM `-Os` 3,425 B, 정책을 파서 안에서 한 번에 적용, 호스트 테스트로 전 분할 위치 검증 가능 |

직접 구현의 위험은 경계값 실수다. 그래서 테스트가 모든 요청을 통째, 1바이트씩, 2바이트씩, 모든 분할 위치, 무작위 분할 64가지로 넣고 결과가 같은지 확인한다. 무작위·변형 입력 2만 건 퍼즈 테스트도 돈다.

## 구조

- 헤더 블록(`\r\n\r\n`까지)을 `hdr[1536]`에 이어 붙이다가, 종결자가 보이면 한 번에 해석·검증한다. 조각 경계에 걸친 종결자도 찾도록 직전 3바이트부터 다시 본다.
- 같은 조각에서 종결자 뒤에 온 바이트는 본문으로 넘긴다.
- 본문은 `Content-Length`만큼 `body[512]`에 바이트 그대로 저장한다. 문자열 규칙을 적용하지 않는다.
- 문자열은 `hdr` 안의 (오프셋, 길이)로 참조한다. 경로만 퍼센트 디코딩해 `path[256]`에 NUL 종료로 둔다.
- 완료나 오류 뒤에는 더 이상 바이트를 소비하지 않는다. 남은 바이트는 `*consumed`로 알려 주고 호출자가 버린다(파이프라이닝 없음, 응답 후 연결 종료).
- 동적 할당 없음. `http_req_init()`이 컨텍스트 전체를 지워 이전 요청의 데이터가 남지 않는다.

## 메모리

| 항목 | 값 | 비고 |
|---|---|---|
| `sizeof(http_req_t)` | 2,350 B | 호스트(x86-64)와 ARM(cortex-m33) 동일, `arm-none-eabi-nm`로 확인 |
| 내역 | 헤더 1,536 + 본문 512 + 경로 256 + 메타데이터 46 | |
| HTTPS 빌드 예상 | 4개(TLS 슬롯과 1:1) = 9,400 B | 1b에서 연결. 기존 `g_req_buf[1024]` 제거 시 순증가 약 8,376 B(계산) |
| 코드 | 3,425 B | ARM `-Os`, 링크 전 오브젝트 |

512 B 본문 한도는 로그인·설정 폼용이다. 인증서 업로드나 펌웨어 업데이트에는 맞지 않는다. 그런 기능은 본문을 버퍼에 다 담지 않고 흘려 받는 별도 경로와 별도 한도가 필요하다.

## 입력 정책

기본 원칙은 **기본 거부**다. 아래에 없는 형태도 문법에 맞지 않으면 거부한다.

| 항목 | 정책 | 응답 |
|---|---|---|
| 요청 줄 형식 | `METHOD SP target SP HTTP/1.x CRLF`, 공백 1개씩 | 400 |
| 메서드 | 1~16자 token. GET·POST만 구분, 나머지는 OTHER(라우터가 405) | 400 / 405 |
| 버전 | HTTP/1.0, HTTP/1.1만 | 505 |
| target | origin-form(`/`로 시작)만. absolute-form, `*` 거부 | 400 |
| 경로 문자 | pchar와 `/`만, `%XX`는 16진 두 자리, 디코딩 후 NUL·제어문자 거부, `..` 세그먼트 거부(인코딩 포함) | 400 |
| 쿼리 | pchar·`/`·`?`·`%XX`, 원문 유지(디코딩은 `http_query_get()` 한곳) | 400 |
| 경로·쿼리 길이 | 경로 디코딩 후 255 B, 쿼리 512 B | 414 |
| 헤더 블록 크기 | 1,536 B(요청 줄 포함) | 431 |
| 줄 끝 | CRLF만. 단독 LF·CR 거부 | 400 |
| 헤더 이름 | token, `:` 앞 공백 금지 | 400 |
| 헤더 접기(obs-fold) | 거부 | 400 |
| NUL | 헤더 블록 어디든 거부 | 400 |
| 값의 제어문자 | HTAB 외 거부, 0x80 이상(obs-text)은 허용 | 400 |
| Host | HTTP/1.1은 정확히 1개. 1.0은 선택, 중복은 거부 | 400 |
| Content-Length | 숫자만(부호·목록 금지), 7자리 이하, 중복은 같은 값이어도 거부 | 400 |
| Content-Length 크기 | 512 초과 | 413 |
| POST에 Content-Length 없음 | 거부 | 411 |
| GET 등에 0이 아닌 본문 | 거부 | 400 |
| Transfer-Encoding | 모든 값 미지원 | 501 |
| Transfer-Encoding + Content-Length | 거부(요청 밀반입 방지) | 400 |
| Expect | 모든 값 거부(100-continue 미지원) | 417 |
| Cookie, Authorization, Content-Type 중복 | 거부 | 400 |
| Connection | 기록만. 서버는 항상 응답 후 종료 | - |
| Upgrade | 무시하고 일반 HTTP/1.1로 처리 | - |
| 본문 뒤 추가 데이터 | 소비하지 않음 | - |
| 불완전한 본문 | `NEED_MORE` 유지. 연결 계층의 제한시간(1b)이 끊음 | (408) |

## 테스트

```
example/WIZnet_Camera_Stream/test/run_host_tests.sh
```

- MinGW gcc로 호스트에서 빌드·실행하고, `arm-none-eabi-gcc`가 있으면 ARM으로도 컴파일해 크기를 출력한다.
- 파서는 `-Wall -Wextra -Werror -Wshadow -Wconversion -Wsign-conversion`으로 컴파일한다.
- 2026-10-23 결과: 26,488 검사 통과, 실패 0. 퍼즈 2만 건(오류 10,973 / 추가 필요 7,908 / 완료 1,119), 컨텍스트 앞뒤 경계값 손상 없음.
- 이 환경의 MinGW 8.1에는 AddressSanitizer가 없다(`-lasan` 없음). 스택 보호 옵션은 C99 printf와 함께 쓰면 첫 호출에서 죽어서 뺐다. 메모리 오류 검사는 경계값(sentinel) 확인으로 대신했다.
