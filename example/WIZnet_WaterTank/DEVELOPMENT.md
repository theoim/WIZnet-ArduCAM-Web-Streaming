# 저수조 부저 감시 장치 — 개발 히스토리

W6300 + RP2350 + I2S 마이크 + ArduCAM Mega 로 만든 저수조 원격 감시 장치의
개발 경과를 정리한 내부 공유용 문서다.

구현 설명서가 아니다. **무엇을 결정했고, 왜 그렇게 결정했으며, 측정 결과가
그 결정을 어떻게 바꿨는지**를 기록한다.

---

## 1. 요구사항

지하실 수조에 수위 경보 부저가 있다. 물이 차면 울리지만 **현장에 상주할 수
없어서 아무도 못 듣는다.**

| 요구 | 내용 |
|---|---|
| 감지 | 부저 소리를 마이크로 듣고 판단 |
| 통보 | Discord로 알림 + 그 순간의 사진 |
| 확인 | 휴대폰에서 포트포워딩된 주소로 접속해 현재 상태 영상 확인 |
| 설정 | 현장에서 IP·해상도·Webhook을 바꿀 수 있을 것 |

핵심 제약은 **수조에 센서를 담그지 않는다**는 것이다. 이미 설치되어 동작 중인
부저를 그대로 쓰고, 그 소리만 듣는다. 배관이나 수조를 건드리지 않으므로 설치가
비침습적이고, 기존 경보 로직을 신뢰할 수 있다.

---

## 2. 전체 구조

```
I2S 마이크 ──PIO/DMA──> Goertzel 분석 ──> 검출기 ──┬─> Discord (TLS)
                                                   ├─> 카메라 캡처
                                                   └─> 웹 패널 상태
ArduCAM Mega ──SPI──> JPEG ──> W6300 ──> MJPEG 스트림
```

소켓 8개를 모두 쓴다.

| 소켓 | 용도 |
|---|---|
| 0 | Discord HTTPS (전송할 때만 열고 닫음) |
| 1–6 | 웹서버 (연결마다 하나, W6300은 listen 소켓이 그대로 연결이 됨) |
| 6 | 부팅 시 DHCP가 잠깐 빌려 씀 (리스너 열기 전) |
| 7 | DNS |

## 3. 단계별 개발 경과

검증되지 않은 부분을 한 번에 합치지 않고, **독립 예제로 하나씩 증명한 뒤**
통합했다. 각 단계는 저장소에 예제로 남아 있다.

### 3-1. 마이크 (`WIZnet_I2S_Mic_Test`)

PIO로 I2S 마스터 수신을 구현하고 INMP441을 붙였다. 여기서 두 가지를 겪었다.

**데이터가 전부 0인데 샘플링 속도는 정확했다.** 배선에서 SCK와 WS가 바뀌어
있었다. 이 경험 때문에 진단 출력을 "프레임 수"와 "데이터 값"으로 분리했다.
**프레임 카운터는 클럭이 돈다는 증거일 뿐 데이터가 온다는 증거가 아니다.**

**샘플이 음수가 되지 않고 DC가 풀스케일의 절반에 머물렀다.** Philips I2S는
WS 변화 다음 클럭에 MSB가 온다. 한 비트 밀어서 부호를 복원했다.

### 3-2. 검출 방식 — 세 번 바뀌었다

이 프로젝트에서 가장 많이 틀렸고, 가장 많이 배운 부분이다.

**(1차) 음량 기준 — 폐기**

실측으로 바로 무너졌다.

| 소리 | rms |
|---|---|
| 박수 | 0.067 (암소음의 16배) |
| 2 kHz 순음 | 0.004~0.008 (**암소음과 동일**) |

**무시해야 할 소리에 반응하고 잡아야 할 소리를 놓친다.**

**(2차) 음조성 기준 — 채택, 그러나 불완전**

Goertzel 필터 뱅크로 1500~4500 Hz를 62.5 Hz 간격 49칸으로 나누고,
`tone_ratio = 최대 칸 ÷ 나머지 칸 평균`을 썼다. 같은 두 소리가 **70배** 차이로
갈렸다. 음량과 달리 거리에 둔감하다는 장점도 있다.

이 단계에서 결정한 것들:

- **연속 N블록 → 3초 창 안의 N블록 (N-of-M)**
  초기 버전은 2초 내내 임계값을 넘어야 했다. 삐-삐- 끊기는 부저는 **쉬는
  구간마다 카운트가 초기화되어 영원히 경보가 안 울린다.** 창 안에서 세는
  방식으로 바꿔 연속음과 단속음을 모두 처리했다.
- **앵커 칸 고정 (±2칸 허용)**
  휴대폰 벨소리가 2125 / 3125 / 2375 / 3375 Hz를 오가며 임계값을 반복해서
  넘었다. 서로 다른 주파수의 적중을 합산하지 않도록 막았다.
- **히스테리시스 (진입 20 / 유지 12)**
  경보 경계에서 상태가 진동하면 알림이 반복 발송된다.

**(3차) 음량 + 지속시간 병행 — 현재**

실제 부저를 현장 조건에서 측정했더니 **음조성 방식이 통하지 않았다.**

| 지표 | 조용한 방 | 부저 울릴 때 |
|---|---|---|
| 최대칸 ÷ 평균 | 4 ~ 12 | **3.4 ~ 5.5** |
| 최대칸 ÷ 중앙값 | 5 ~ 15 | **3.6 ~ 6.0** |
| 연속 5칸 ÷ 중앙값 | 3 ~ 9 | **2.3 ~ 4.4** |
| **rms** | 0.004 ~ 0.008 | **0.012 ~ 0.016** |

**모양을 재는 지표 세 개가 모두 조용할 때보다 부저일 때 더 낮았다.** 그 부저는
솟는 칸이 없다. 방 소음과 같은 모양이고 크기만 2~4배 큰 넓은 잡음이다.
분모(배경)를 평균에서 중앙값으로 바꿔도 결과는 같았다.

갈라지는 것은 음량 하나뿐이었다. 1차에서 폐기한 그 지표다.

그래서 **음량을 다시 쓰되, 임계값이 아니라 지속시간으로 박수와 구별한다.**

```
박수   : 1~2블록 (0.03초)
부저   : 수백 블록 (수 초)
```

조건은 **"학습된 방 소음의 2.2배 이상인 블록이 3초 창 안에 1초치(62개)"** 다.
방 소음 기준선은 약 30초 평균으로 스스로 학습하고, **이미 시끄럽거나 경보
중일 때는 학습을 멈춘다.** 기준선이 부저를 따라 올라가면 부저가 울리는 중에
경보가 해제되기 때문이다.

음조성 경로는 남겨뒀다. **둘 중 하나만 걸려도 경보**이고, 어느 쪽이 걸렸는지
로그와 알림에 표시한다. 실제로 이 부저는 울리기 직전 2062 Hz의 희미한 소리를
내는데, 음조성 경로가 그걸 먼저 잡아 더 이른 예고가 된다.

> **남은 과제:** 거리가 가장 큰 변수다. 멀리서는 음조성이 13~16으로 암소음
> 최고치(18.8)보다 낮다. **소프트웨어로 해결되지 않는다.** 마이크를 부저
> 가까이 설치할 수 있는지가 설치 조건이다.

### 3-3. Discord 전송 (`WIZnet_Discord_Test`)

기존 wiz-claw HTTPS 클라이언트에서 **웹훅에 필요한 최소한만** 가져왔다.
원본 5,940줄 중 1,596줄(27%)만 포팅했다. Telegram·LLM 관련 헤더는 주석만 있는
타입이거나 cJSON을 끌고 들어와서 제거했다.

mbedTLS 설정에 ECDSA 관련 11줄을 추가했다. discord.com은 ECDSA 체인
(`discord.com ← WE1 ← GTS Root R4`)을 쓴다. 빠지면 핸드셰이크가 인증서 파싱이나
서명 검증에서 실패하는데, **밖에서 보면 네트워크 장애와 구별되지 않는다.**

사진 전송은 `multipart/form-data`로 구현했다. 실측 전송 시간은 **6.7~7.1초**이고
그중 사진 데이터 자체는 400 ms 뿐이다. 나머지는 DNS와 TLS 핸드셰이크다.

### 3-4. 통합 (`WIZnet_WaterTank`)

마이크·검출기·카메라·웹서버·Discord를 한 펌웨어로 합쳤다.

## 4. 통합 후 겪은 문제와 결정

독립 예제에서는 안 보이고 **합친 뒤에야 드러난** 문제들이다.

### 4-1. 웹서버가 마이크를 굶겼다

통합하자마자 부저를 못 잡았다. 추측하지 않고 계측했다.

```
스트림 없음 : blk/s 62   ovr 고정
HD 스트림 중 : blk/s 24   ovr 초당 +11
```

**블록의 60%를 버리고 있었다.** HD 한 장을 보내는 데 걸리는 시간이 DMA 버퍼
하나가 담는 시간보다 길었다. 세 단계로 고쳤다.

| 조치 | 근거 |
|---|---|
| DMA 버퍼 1블록 → 8블록 (16 ms → 128 ms) | 캡처 100 ms를 버퍼 안에 넣는다 |
| 스트림 간격 500 ms (2 fps) | 수조 감시에 그 이상은 불필요 |
| **전송을 비차단으로 전환** | 버퍼 크기로는 못 막는 문제였다 |

마지막이 핵심이다. 네트워크 전송은 **최대 3초까지 기다릴 수 있어서 어떤 버퍼
크기로도 덮을 수 없다.** 소켓을 `SF_IO_NONBLOCK`으로 열고, 프레임을 `포인터 +
남은 길이`로 들고 있다가 루프마다 2 KB씩만 밀어넣는 방식으로 바꿨다.
**어디서도 기다리지 않는다.**

### 4-2. 스트림 연결이 쌓였다

페이지는 프레임이 끊기면 재연결하고, 전파가 끊긴 폰은 10초간 소켓을 쥐고 있다.
스트림이 여러 개 살아남으면 루프 한 바퀴가 수백 ms가 되고, 6개가 전부
스트림이면 **새 접속을 받을 소켓이 없다.**

→ **스트림은 항상 1개.** 새 요청이 오면 이전 것을 닫는다. 소켓도 3개에서 6개로
늘리고 TCP keepalive(10초)를 걸었다.

### 4-3. 설정 저장이 한 번도 성공한 적이 없었다

`플래시 쓰기에 실패했습니다`의 원인은 코드 한 줄이었다.

```c
if (sizeof(s) > FLASH_PAGE_SIZE) return false;   /* 292 > 256 → 항상 false */
```

Webhook URL 칸을 192바이트로 잡은 순간 구조체가 플래시 페이지(256B)를 넘었고,
그 뒤 **모든 SAVE가 플래시를 건드리지도 않고 실패를 반환했다.** 스테이징 버퍼를
페이지 단위로 올림(2페이지)하고, 런타임 검사를 빌드 타임 `_Static_assert`로
바꿨다. 크기 초과는 이제 컴파일이 안 된다.

### 4-4. HD가 적용되지 않았다

해상도를 바꿔도 화질이 그대로였다. 전시회 예제에 이미 기록되어 있던 함정이다.

```c
set_pixel_format(JPEG);
set_frame_size(HD);     // 대기 없이 붙이면 해상도 쓰기가 조용히 씹힌다
```

콘솔은 `camera at HD`를 찍는다. **자기 변수를 출력한 것이고 센서에는 물어보지
않았기 때문이다.** 앞뒤로 200 ms 대기를 넣고 반환값을 검사하도록 고쳤다.

→ **교훈: 장치에 쓴 값을 출력하지 말고, 쓰기의 성공 여부를 출력한다.**

### 4-5. DHCP가 성공하고도 실패로 처리됐다

```
[I] DHCP assigned      ← 공유기가 주소를 줬다
[E] DHCP timeout       ← 60초 기다리다 포기했다
```

ioLibrary의 `DHCP_run()`은 주소를 받는 그 한 번만 `DHCP_IP_ASSIGN`을 반환하고
이후 `DHCP_IP_LEASED`를 반환한다. 그런데 **assign 콜백이 불리는 호출에서는
반환값이 아직 `DHCP_RUNNING`이다.** `LEASED`를 성공으로 받지 않던 포트 코드가
그 순간을 놓치고 타임아웃까지 기다렸다. `port/wiz-claw/src/wiz_claw_net.c`에서
수정했다.

## 5. 설계 결정 기록

### 5-1. 스트리밍은 항상 켜둔다

초기에는 경보 중에만 포트와 카메라를 열었다. "1년에 한 시간 열리는 포트가 1년
내내 열린 포트보다 작은 표적"이라는 논리였다.

그 대가가 더 컸다. **"지하실이 왜 조용한지" 확인하려는 사람이 비상시에만
답하는 패널을 확인할 수 없다.** 확인할 수 없는 제어판은 신뢰받지 못하고,
신뢰받지 못하는 장치는 결국 지하실로 직접 내려가는 것으로 대체된다.

닫힌 포트 대신 **토큰**이 그 역할을 한다. 토큰 없는 요청은 401이나 403이 아니라
**404**를 받는다. 스캐너가 경로의 존재조차 알 수 없게 하기 위해서다.

### 5-2. 내부망에서는 토큰을 요구하지 않는다

처음 설치하는 사람은 Webhook을 설정하러 패널에 들어가야 하는데, **그 토큰은
Webhook 메시지로 받는다.** 닭과 달걀이다.

→ **같은 서브넷에서 온 요청은 토큰을 묻지 않는다.** 포트포워딩으로 들어오는
요청은 공인 IP를 달고 오므로 사설 대역과 절대 맞지 않는다. **인터넷 쪽 문은
그대로 잠겨 있다.**

대가는 명시한다. 같은 공유기에 붙은 사람은 누구나 영상을 볼 수 있다. 지하실
수조라면 그들은 계단을 내려가 직접 볼 수 있는 사람들과 같은 집단이다.

### 5-3. 펌웨어를 올리면 설정이 초기화된다

펌웨어 이미지 전체의 체크섬을 설정과 함께 저장하고 부팅 시 비교한다.

| 상황 | 동작 |
|---|---|
| 리셋·전원 재투입 (같은 이미지) | **설정 유지** |
| 펌웨어 업로드 (다른 이미지) | **설정 폐기 → 기본값** |

개발 중인 보드는 몇 분마다 새 코드를 받는다. 두 빌드 전에 저장된 설정이
조용히 이기면, **적용된 적 없는 기본값을 들여다보며 오후를 보내게 된다.**

`__DATE__`/`__TIME__`을 쓰지 않은 이유: 그 매크로는 자기가 들어있는 파일이 다시
컴파일될 때만 바뀐다. `main.c`만 고치면 `settings.c`는 재컴파일되지 않아
**서로 다른 펌웨어가 같은 신분을 주장한다.**

### 5-4. 비밀값은 저장소에 두지 않는다

Webhook URL은 그 채널에 글을 쓸 수 있는 비밀번호다. 토큰은 카메라와 인터넷
사이에 선 유일한 장벽이다. 둘 다 `config.h`에 리터럴로 있었고, 이는 **모든
빌드·모든 콘솔 로그·모든 화면 공유에 들어가며, `git add` 한 번이면 저장소
역사에 영구히 남는다는 뜻이다.** 나중에 지워도 역사에서는 지워지지 않는다.

→ `secrets.h`(커밋 제외) + `secrets.h.example`(커밋) 구조로 분리했다.
**Webhook이 없어도 보드는 정상 기동한다.** 감시하고, 패널을 띄우고, 콘솔에
경보를 남긴다. 알릴 데가 없을 뿐이다. 채팅 서비스 주소가 없다고 부팅을
거부하는 것은 말이 안 된다. 다만 **토큰이 없으면 멈춘다.** 토큰 없이 부팅하면
카메라가 공개되기 때문이다.

### 5-5. 패널은 저장값이 아니라 동작 중인 값을 보여준다

DHCP일 때 패널은 저장된 예비 주소를, 보드는 공유기가 준 주소를 쓰고 있었다.
같은 화면에 숫자 두 벌이 있으면 읽는 사람이 어느 쪽이 진짜인지 판단해야 한다.

더 실질적인 문제는 **STATIC 버튼이 뜻대로 동작하지 않는 것**이었다. DHCP로
`.9`를 받은 상태에서 STATIC을 누르고 저장하면, 화면에 보이던 예비 주소 `.7`이
저장되어 **보드가 다른 곳에서 올라왔다.**

→ 입력칸을 칩에서 읽은 현재 값으로 채운다. STATIC + SAVE는 **지금 쓰는 주소를
그대로 고정한다.** 버튼 이름이 뜻하는 대로다.

### 5-6. 해상도는 즉시 적용, 주소는 재시작

| 설정 | 적용 시점 | 이유 |
|---|---|---|
| 해상도 | **즉시** | 센서 레지스터 하나. 캡처 버퍼는 모드와 무관하게 200 KB 고정 |
| 주소 | 재시작 | 리스닝 소켓이 그 주소로 열려 있고, 접속 중인 폰도 그 주소를 쓴다 |

해상도를 확인하려고 저장하고 재시작까지 기다려야 한다면, **그 설정은
조정되지 않고 방치된다.**

## 6. 현재 상태

### 동작 확인됨

- I2S 마이크 수신, Goertzel 분석, 두 경로 검출
- Discord 텍스트/사진 전송 (TLS 1.2, ECDHE-ECDSA)
- MJPEG 스트리밍 (HD 1280×720, 2 fps)
- 플래시 설정 저장, 펌웨어 교체 시 초기화
- DHCP / STATIC 전환, 실패 시 고정 주소 폴백
- 웹 패널 (LIVE / CONFIG 탭, 상태 바 2개, LED 2개)

### 측정값

| 항목 | 값 |
|---|---|
| 오디오 블록 | 62.5 블록/초 (16 kHz, 256 샘플) |
| 스캔 대역 | 1500~4500 Hz (49칸) + 312~1437 Hz (19칸, 로그용) |
| HD 프레임 | 약 45 KB |
| Discord 전송 | 6.7~7.1초 (사진 데이터는 400 ms) |
| 경보 해제 | 무음 15초 |

### 남은 과제

1. **마이크–부저 거리.** 가장 큰 변수이고 소프트웨어로 해결되지 않는다.
2. **조명.** 야간에는 사진이 검게 나온다. ArduCAM Mega의 IR 차단 필터 때문에
   적외선 LED는 효과가 없을 가능성이 높다.
3. **Discord 전송 중 7초간 미감지.** TLS 전송이 루프를 점유한다. 카메라·웹서버와
   함께 **코어 1로 옮기면 함께 해결된다.** RP2350은 코어가 둘이고 현재 하나만
   쓰고 있다.
4. **DHCP 리스 갱신 없음.** 받은 주소를 고정처럼 쓴다. 리스 만료 후 공유기가
   그 주소를 다른 장비에 주면 전원 재투입이 필요하다. **공유기에 DHCP 예약을
   거는 것이 올바른 해법이다.**

## 7. 이 프로젝트에서 반복된 교훈

**예상한 문제를 고치지 말고, 계측한 문제를 고친다.**

이 문서에 기록된 주요 문제 중 추측으로 맞힌 것은 하나도 없다.

| 증상 | 처음 추측 | 실제 원인 |
|---|---|---|
| 부저를 못 잡는다 | 임계값이 높다 | 음조성 지표 자체가 부적합 |
| 통합 후 감지 실패 | 부저가 작다 | 웹서버가 오디오 블록을 버림 |
| 설정이 저장 안 됨 | 플래시 수명/타이밍 | 구조체가 페이지 크기 초과 |
| HD가 안 먹음 | 설정이 저장 안 됨 | 센서 쓰기가 타이밍 때문에 씹힘 |
| DHCP 실패 | 공유기 설정 | 반환값 하나를 성공으로 안 받음 |

**밖에서 보면 전부 똑같이 보인다.** 그래서 숫자를 먼저 본다.

## 8. 빌드

```bash
cp example/WIZnet_WaterTank/secrets.h.example example/WIZnet_WaterTank/secrets.h
# secrets.h 를 채운다 (최소한 STREAM_TOKEN)

mkdir build && cd build
cmake .. -G "Unix Makefiles"
cmake --build . --target watertank -j 8
```

`build/example/WIZnet_WaterTank/watertank.uf2` 를 보드에 복사한다.

### 핀 배치

| 신호 | 핀 |
|---|---|
| I2S BCLK | GP2 |
| I2S WS | GP3 (BCLK+1, PIO가 연속 핀을 요구) |
| I2S SD | GP28 |
| 부저 감지 LED | GP25 |
| RUN LED | GP26 |

카메라와 W6300 핀은 TOE 스트리밍 예제와 동일하다.

### 진단 출력

평소에는 네트워크·경보 이벤트만 출력한다. 마이크 수치를 보려면
`config.h`에서 한 줄을 바꾼다.

```c
#define MIC_DEBUG_LOG  1
```

```
[19칸|49칸] hi 2062 t 20.0 | lo 1062 t 4.5 | T 4/12 L 23/62 | rms0.0075 base0.0051 1.5x | blk64 ovr51 watch
```

`[audio] ... lost during the last 10 s` 가 출력되면 루프가 막히고 있다는 뜻이다.
Discord 전송 중 손실은 따로 표시되며 정상 비용이다.
